## TS스터디 27일차: 아이템 59 (7장)

### 아이템 59: 완전성 체크를 위해 never 타입 사용하기

정적 타입 분석은 발생하면 안 되는 일을 찾아낼 때 사용할 수 있는 훌륭한 방법이다.

반대로 어떤 행위를 반드시 해야 하지만, 하지 않아서 발생하는 오류도 존재한다.

TS 자체만으로는 위 경우를 모두 잡기 힘듦

완전성 체크 기법으로 해결!

`switch`문의 `default`에서 값이 `never` 타입인지 검사하고, 이후 코드가 변경됐을 때 여전히 `never`인지 확인하는 방법이 완전성 체크 기법이다.

```ts
function assertNever(value: never): never {
  throw new Error(`처리하지 않은 값: ${value}`);
}

function getArea(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':
      return Math.PI * shape.radius ** 2;

    case 'square':
      return shape.size ** 2;

    default:
      return assertNever(shape);
  }
}
```

`Shape`에 새로운 종류가 추가됐는데 `case`문을 작성하지 않으면, `default`에 도달한 `shape`가 더 이상 `never`가 아니게 되므로 타입 오류가 발생한다.

안전성을 높이기 위해서 반환 타입 명시와 `never` 검사, `satisfies` 연산자 등을 사용하는 것이 좋다.

> 한 유니온의 모든 경우를 검사하려면 `never`를 활용한다.  
> 함수의 반환 타입도 명시해 누락된 반환 경로를 검사한다.

## TS스터디 28일차: 아이템 60~61

### 아이템 60: 객체를 순회하는 노하우 이해하기

`for`문에서 객체를 순회할 때 `const k in obj`라고 작성하면 `k`는 `string` 타입이 된다.

그래서 `k`를 `keyof typeof obj`로 단언하면 오류는 사라진다.

#### 왜 string으로 추론됐을까?

함수에서 받은 매개변수 값인 객체를 순회한다고 했을 때, 구조적 타이핑에 의해 선언된 객체의 속성보다 더 많은 속성을 포함한 채로 받을 수 있다.

따라서 TS는 `k`를 객체에 선언된 키로 제한하지 않고, 더 넓은 타입인 `string`으로 선택할 수밖에 없다.

#### keyof 단언을 사용할 때의 문제점

`let k: keyof typeof obj` 형태의 반복자를 사용할 수도 있지만, 타입 단언보다 안전하다고 할 수 없다.

타입 문제없이 단지 객체의 키와 값을 순회하고 싶은 경우라면 `Object.entries`를 사용하면 된다.

그냥 사용하면 프로토타입 오염 문제 때문에 이슈가 있을 수 있다.

더 정밀한 타입을 얻는 안전한 방법은 키를 명시적으로 나열하는 것이다.

그렇지만 실제 객체의 키와 지역 변수인 키 배열을 일치된 상태로 유지할 방법이 필요하다.

객체 순회는 위험성이 높지만 `Map`을 순회할 때는 그렇지 않다.

### 아이템 61: 레코드 타입을 사용해 값 동기화하기

산점도?

어떤 값은 변경되더라도 트리거를 유발하지 말아야 할 때, 반복문에서 해당 속성을 제외한 모든 속성을 `true`로 처리하는 방식으로 최적화할 수 있다.

이를 실패에 열린 접근법 또는 보수적 접근법이라고 한다.

또는 OR 연산자를 통해서 트리거되는 경우를 직접 검사할 수도 있다.

그렇지만 위 두 방식은 이상적이지 않다.

새로운 속성이 추가될 때마다 개발자가 직접 메서드를 고치도록 유도하는 것이 좋다.

그렇다고 주석으로만 남겨 놓을 수는 없다.

타입 체커에게 대신 맡겨라!

핵심은 매핑된 타입과 객체 사용이다.

`Record`로 객체를 매핑해 놓고 `true`와 `false`를 조정하는 방식으로, 필드가 추가되면 개발자가 타입을 고치도록 유도할 수 있다.

> 정확도를 희생하며 성능을 추구해서는 안 된다!  
> 존재하는 모든 속성에 대해 다시 그릴지 여부를 빠짐없이 결정하라.

## TS스터디 29일차: 아이템 62~64

### 아이템 62: 가변 함수 모델링을 위해 나머지 매개변수와 튜플 타입 사용하기

웹 앱의 다양한 진입 경로를 표현하는 인터페이스를 예시로 살펴보자.

```ts
interface RouteQueryParams {
  '/': null;
  '/search': {
    query: string;
    language?: string;
  };
  // ...
}
```

URL을 만드는 메서드의 쿼리 타입을 위 타입으로 지정하면 안전해 보인다.

하지만 두 번째 매개변수인 `params`가 경로와 관계없이 설정될 수 있다면 안전하지 않을 수 있다.

`params`의 타입이 `route`에 따라 결정되도록 만들면 더 안전하다.

그런데 `/search` 경로는 정상적으로 동작하지만, 루트 경로인 `/`를 사용할 때는 불필요하게 두 번째 값으로 `null`을 전달해야 한다.

```ts
function buildURL<Path extends keyof RouteQueryParams>(
  route: Path,
  ...args: RouteQueryParams[Path] extends null
    ? []
    : [params: RouteQueryParams[Path]]
) {
  const params = args.length > 0 ? args[0] : null;

  return route + (params ? '...' : '');
}
```

호출부를 보면 실제로 경우에 따라 두 가지 다른 함수가 있는 것처럼 보인다.

```ts
buildURL('/');
buildURL('/search', {
  query: 'typescript',
  language: 'ko',
});
```

결국 첫 번째 매개변수인 `route`와 두 번째 매개변수인 `params` 사이에 연관성을 만드는 것이 중요하다.

경로에 따라 매개변수의 개수나 타입이 달라지기 때문에 나머지 매개변수와 튜플 타입을 사용해서 모델링할 수 있다.

### 아이템 63: 배타적 OR를 모델링하기 위해 선택적 never 속성 사용하기

일반적으로 우리는 OR를 XOR, 즉 배타적 OR의 의미로 생각하기 쉽다.

하지만 개발자와 논리학자가 말하는 일반적인 OR는 IOR, 즉 포함적 OR를 의미한다.

#### 이게 무슨 말일까?

우리가 논리적으로 생각할 때 `A | B`의 의미는 “A 또는 B”라는 뜻이다.

그렇지만 TS의 유니온은 포함적 OR이기 때문에 A이거나 B이거나, A와 B의 속성을 모두 포함하는 값도 허용될 수 있다.

우리는 그 이유를 알고 있다.

구조적 타이핑 때문!

정말로 XOR가 필요한 경우에는 두 인터페이스가 명확하게 구분되어야 한다.

선택적 `never`를 사용하면 특정 속성을 차단할 수 있다.

```ts
interface One {
  a: string;
  b?: never;
}

interface Two {
  b: string;
  a?: never;
}

type ExclusiveThing = One | Two;
```

`One`에는 `b`를 넣을 수 없고, `Two`에는 `a`를 넣을 수 없다.

`never` 타입에는 어떠한 값도 할당할 수 없기 때문에 두 속성을 모두 가진 값은 타입 체커를 통과할 수 없다.

그렇지만 해당 속성이 선택 사항이기 때문에 허용되는 경우가 있다.

속성 자체를 갖지 않는 것

XOR를 구현하기 위해 태그된 유니온을 사용할 수도 있다.

타입에 `type`과 같은 구분 필드를 명시하는 방법이다.

직접 선택적 `never`를 추가하는 대신 제네릭 XOR 헬퍼를 정의하는 것도 가능하다.

```ts
type XOR<T1, T2> =
  | (T1 & {
      [K in Exclude<keyof T2, keyof T1>]?: never;
    })
  | (T2 & {
      [K in Exclude<keyof T1, keyof T2>]?: never;
    });
```

### 아이템 64: 공식 명칭에는 상표 붙이기

태그된 유니온에도 단점이 있다.

어쨌든 실제 객체에 구분 필드를 추가하는 것은 비용이기 때문이다.

타입 시스템에서만 동작하면서도 명시적 태그와 비슷한 효과를 얻는 방법이 있다.

이러한 맥락에서 태그는 상표 또는 브랜드라고도 불린다.

런타임 오버헤드가 없으며 기본형 타입에도 적용할 수 있다.

명목적 타이핑?

TS는 일반적인 문자열만 보고 해당 값이 절대 경로인지 상대 경로인지 판단하기 어렵다.

이럴 때 상표 기법을 사용할 수 있다.

```ts
type AbsolutePath = string & {
  _brand: 'abs';
};
```

일반적인 값으로는 `string`이면서 `_brand` 속성까지 가진 값을 만들기 어렵다.

따라서 타입에 일종의 도장을 찍어 타입 시스템의 영역에만 존재하도록 만든다.

절대 경로인지 실제로 검사하는 함수를 만들고, 조건문으로 검사한 뒤 타입 단언이나 사용자 정의 타입 가드를 사용해 `AbsolutePath`로 변환할 수 있다.

위와 같은 맥락으로 숫자에도 상표를 붙일 수 있다.

#### 상표를 붙이는 다른 기법

`private` 필드로 클래스에 상표 붙이기

문자열 기반 `enum` 타입을 만들고 인터섹션으로 활용하기

고유한 심벌 타입인 `unique symbol` 사용하기

상표 심벌이 외부에 노출되지 않으면 임의로 상표 타입의 값을 만들기 어렵다.

따라서 해당 타입의 값을 얻으려면 타입 단언이나 검증용 헬퍼 함수를 사용해야 한다.
