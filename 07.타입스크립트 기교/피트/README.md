## TS스터디 27일차: 아이템 59 (7장)

### 아이템 59: 완전성 체크를 위해 never 타입 사용하기

정적 타입 분석은 발생하면 안 되는 일을 찾아낼 때 사용할 수 있는 훌륭한 방법이다.

반대로 어떤 행위를 반드시 해야 하지만, 하지 않아서 발생하는 오류도 존재한다.

TS 자체만으로는 위 경우를 모두 잡기 힘듦

완전성 체크 기법으로 해결!

`switch`문의 `default`에서 값이 `never` 타입인지 검사하고, 이후 코드가 변경됐을 때 여전히 `never`인지 확인하는 방법이 완전성 체크 기법이다.

```ts
function assertNever(value: never): never {
  throw new Error(`처리하지 않은 값: ${value}`);
}

function getArea(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':
      return Math.PI * shape.radius ** 2;

    case 'square':
      return shape.size ** 2;

    default:
      return assertNever(shape);
  }
}
```

`Shape`에 새로운 종류가 추가됐는데 `case`문을 작성하지 않으면, `default`에 도달한 `shape`가 더 이상 `never`가 아니게 되므로 타입 오류가 발생한다.

안전성을 높이기 위해서 반환 타입 명시와 `never` 검사, `satisfies` 연산자 등을 사용하는 것이 좋다.

> 한 유니온의 모든 경우를 검사하려면 `never`를 활용한다.  
> 함수의 반환 타입도 명시해 누락된 반환 경로를 검사한다.

## TS스터디 28일차: 아이템 60~61

### 아이템 60: 객체를 순회하는 노하우 이해하기

`for`문에서 객체를 순회할 때 `const k in obj`라고 작성하면 `k`는 `string` 타입이 된다.

그래서 `k`를 `keyof typeof obj`로 단언하면 오류는 사라진다.

#### 왜 string으로 추론됐을까?

함수에서 받은 매개변수 값인 객체를 순회한다고 했을 때, 구조적 타이핑에 의해 선언된 객체의 속성보다 더 많은 속성을 포함한 채로 받을 수 있다.

따라서 TS는 `k`를 객체에 선언된 키로 제한하지 않고, 더 넓은 타입인 `string`으로 선택할 수밖에 없다.

#### keyof 단언을 사용할 때의 문제점

`let k: keyof typeof obj` 형태의 반복자를 사용할 수도 있지만, 타입 단언보다 안전하다고 할 수 없다.

타입 문제없이 단지 객체의 키와 값을 순회하고 싶은 경우라면 `Object.entries`를 사용하면 된다.

그냥 사용하면 프로토타입 오염 문제 때문에 이슈가 있을 수 있다.

더 정밀한 타입을 얻는 안전한 방법은 키를 명시적으로 나열하는 것이다.

그렇지만 실제 객체의 키와 지역 변수인 키 배열을 일치된 상태로 유지할 방법이 필요하다.

객체 순회는 위험성이 높지만 `Map`을 순회할 때는 그렇지 않다.

### 아이템 61: 레코드 타입을 사용해 값 동기화하기

산점도?

어떤 값은 변경되더라도 트리거를 유발하지 말아야 할 때, 반복문에서 해당 속성을 제외한 모든 속성을 `true`로 처리하는 방식으로 최적화할 수 있다.

이를 실패에 열린 접근법 또는 보수적 접근법이라고 한다.

또는 OR 연산자를 통해서 트리거되는 경우를 직접 검사할 수도 있다.

그렇지만 위 두 방식은 이상적이지 않다.

새로운 속성이 추가될 때마다 개발자가 직접 메서드를 고치도록 유도하는 것이 좋다.

그렇다고 주석으로만 남겨 놓을 수는 없다.

타입 체커에게 대신 맡겨라!

핵심은 매핑된 타입과 객체 사용이다.

`Record`로 객체를 매핑해 놓고 `true`와 `false`를 조정하는 방식으로, 필드가 추가되면 개발자가 타입을 고치도록 유도할 수 있다.

> 정확도를 희생하며 성능을 추구해서는 안 된다!  
> 존재하는 모든 속성에 대해 다시 그릴지 여부를 빠짐없이 결정하라.
