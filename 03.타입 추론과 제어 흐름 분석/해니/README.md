### 아이템 18. 추론 가능한 타입을 사용해 장황한 코드 방지하기

타입 구문은 적을수록 좋다.
타입스크립트가 알아낼 수 있는 것을 손으로 적는 건 중복이고, 리팩터링할 때 고쳐야 할 곳만 늘어난다.
지역 변수, 구조 분해로 꺼낸 값, 기본값이 있는 파라미터, 타입이 정의된 라이브러리의 콜백 인자는 모두 추론에 맡긴다.

명시적 타입 구문은 **타입스크립트가 스스로 판단하기 어려운 상황**에 쓴다.

**객체 리터럴** - 타입을 명시하면 잉여 속성 체크가 켜져서 오타를 선언한 자리에서 잡을 수 있다. 다만 `: Type`을 붙이면 추론된 좁은 타입을 잃는다. TS 4.9부터는 `satisfies`를 쓰면 잉여 속성 체크를 받으면서 좁은 타입도 유지된다. 상수 설정 객체에는 `satisfies`가 거의 항상 낫다.

**함수의 반환 타입** - 명시하지 않으면 구현부의 실수가 호출부 오류로 둔갑한다. 미리 적어두면 오류가 함수 안에서 잡히고, 시그니처 자체가 문서가 되며, 명명된 타입이 인라인으로 펼쳐지지 않는다. `return`이 여러 개인 함수에 특히 효과가 크다.

| 상황                             | 권장                           |
| -------------------------------- | ------------------------------ |
| 지역 변수, 구조 분해, 콜백 인자  | 추론에 맡긴다                  |
| 객체 리터럴 상수                 | `satisfies`로 검증 + 추론 유지 |
| 함수 파라미터                    | 항상 명시 (추론 불가)          |
| 외부에 공개하는 함수의 반환 타입 | 명시                           |
| 모듈 내부 헬퍼의 반환 타입       | 추론에 맡겨도 무방             |

### 아이템 19. 다른 타입에는 다른 변수 사용하기

**변수의 값은 바뀌어도 타입은 바뀌지 않는다.**
`let`으로 선언한 변수의 타입은 최초 선언 시점에 결정되고, 이후 좁혀질 뿐 바뀌지 않는다.

억지로 유니온 타입을 만들어 한 변수를 재사용하면 쓸 때마다 타입을 확인해야 하는 비용이 생긴다. 타입이 다른 값에는 별도의 변수를 쓴다.

- 서로 관련 없는 두 값이 분리된다
- 변수명을 더 구체적으로 지을 수 있다
- 타입 추론이 좋아지고 타입 구문이 불필요해진다
- 유니온 대신 단일 타입이라 간결하다
- `const`로 선언할 수 있다

스코프가 다르면 같은 이름을 써도 문법적으로 문제없지만, 혼란을 줄 수 있으니 이름 자체를 다르게 짓는 편이 낫다. 변수를 재사용하고 싶은 유혹이 든다면 이름이 충분히 구체적이지 않다는 신호다.
