### 아이템 18. 추론 가능한 타입을 사용해 장황한 코드 방지하기

타입 구문은 적을수록 좋다.
타입스크립트가 알아낼 수 있는 것을 손으로 적는 건 중복이고, 리팩터링할 때 고쳐야 할 곳만 늘어난다.
지역 변수, 구조 분해로 꺼낸 값, 기본값이 있는 파라미터, 타입이 정의된 라이브러리의 콜백 인자는 모두 추론에 맡긴다.

명시적 타입 구문은 **타입스크립트가 스스로 판단하기 어려운 상황**에 쓴다.

**객체 리터럴** - 타입을 명시하면 잉여 속성 체크가 켜져서 오타를 선언한 자리에서 잡을 수 있다. 다만 `: Type`을 붙이면 추론된 좁은 타입을 잃는다. TS 4.9부터는 `satisfies`를 쓰면 잉여 속성 체크를 받으면서 좁은 타입도 유지된다. 상수 설정 객체에는 `satisfies`가 거의 항상 낫다.

**함수의 반환 타입** - 명시하지 않으면 구현부의 실수가 호출부 오류로 둔갑한다. 미리 적어두면 오류가 함수 안에서 잡히고, 시그니처 자체가 문서가 되며, 명명된 타입이 인라인으로 펼쳐지지 않는다. `return`이 여러 개인 함수에 특히 효과가 크다.

| 상황                             | 권장                           |
| -------------------------------- | ------------------------------ |
| 지역 변수, 구조 분해, 콜백 인자  | 추론에 맡긴다                  |
| 객체 리터럴 상수                 | `satisfies`로 검증 + 추론 유지 |
| 함수 파라미터                    | 항상 명시 (추론 불가)          |
| 외부에 공개하는 함수의 반환 타입 | 명시                           |
| 모듈 내부 헬퍼의 반환 타입       | 추론에 맡겨도 무방             |

### 아이템 19. 다른 타입에는 다른 변수 사용하기

**변수의 값은 바뀌어도 타입은 바뀌지 않는다.**
`let`으로 선언한 변수의 타입은 최초 선언 시점에 결정되고, 이후 좁혀질 뿐 바뀌지 않는다.

억지로 유니온 타입을 만들어 한 변수를 재사용하면 쓸 때마다 타입을 확인해야 하는 비용이 생긴다. 타입이 다른 값에는 별도의 변수를 쓴다.

- 서로 관련 없는 두 값이 분리된다
- 변수명을 더 구체적으로 지을 수 있다
- 타입 추론이 좋아지고 타입 구문이 불필요해진다
- 유니온 대신 단일 타입이라 간결하다
- `const`로 선언할 수 있다

스코프가 다르면 같은 이름을 써도 문법적으로 문제없지만, 혼란을 줄 수 있으니 이름 자체를 다르게 짓는 편이 낫다. 변수를 재사용하고 싶은 유혹이 든다면 이름이 충분히 구체적이지 않다는 신호다.

### 아이템 20. 변수의 타입이 결정되는 원리 이해하기

#### 타입이 어디서 오는가?

TypeScript에서 변수의 타입은 3가지 방식으로 결정된다.

#### 1. **명시적 타입 어노테이션**

타입을 직접 지정하는 방식. 가장 명확하고 혼동의 여지가 없다.

#### 2. **타입 추론 (Type Inference)**

변수를 **선언과 동시에 초기화**하면, TypeScript는 그 값으로부터 타입을 자동으로 추론한다. 선언만 하고 나중에 초기화하면 타입이 `any`가 되므로 권장하지 않는다.

#### 3. **컨텍스트 기반 타입 지정 (Contextual Typing)**

함수가 어디에 쓰이는지에 따라 파라미터의 타입이 자동으로 결정된다. 콜백 함수의 파라미터나 이벤트 핸들러의 파라미터 타입이 이렇게 결정된다.

#### 선언과 초기화를 함께 하자

변수를 선언만 하면 컴파일러가 "아직 뭘 받을지 몰라"라고 생각해서 `any` 타입이 된다. 선언과 초기화를 함께 하면 컴파일러가 타입을 명확히 추론할 수 있다. 명확한 타입은 더 나은 에러 메시지, IDE 자동완성, 타입 안정성을 제공한다.

### 아이템 21. 객체는 한 번에 생성하기

#### 문제: 객체를 부분적으로 구성하면 타입 추론이 헷갈린다

객체를 빈 상태로 선언하면 TypeScript는 그 순간 객체의 타입을 **빈 객체**로 결정해버린다. 나중에 속성을 추가하려고 하면 에러가 발생한다.

#### 해결책: 객체를 한 번에 정의하기

한 번에 모든 속성을 정의하면 TypeScript가 전체 형태를 한눈에 파악할 수 있고, 타입 추론이 정확해진다.

#### 부분적 구성이 필요한 경우

인터페이스 타입을 명시하고 한 번에 모든 속성을 정의해야 한다. 선택적 속성이 있더라도 한 번에 객체를 만드는 것이 좋다. 구성 로직이 복잡하면 함수를 만들어서 완성된 객체를 반환하는 방식이 더 타입 안전하다.

### 아이템 22. 타입 좁히기

타입 좁히기는 변수가 가질 수 있는 타입의 집합을 점진적으로 좁혀나가는 과정이다.

- 초기: 넓은 타입 (예: `string | number`)
- 조건문 이후: 좁혀진 타입 (예: `string`)

#### 타입 별칭과 타입 좁히기의 문제

타입 별칭을 사용하면 **타입 좁히기가 제대로 작동하지 않을 수 있다**는 점이 중요하다.

```typescript
type Named = { kind: "named"; name: string };
type Unnamed = { kind: "unnamed" };
type Thing = Named | Unnamed;

const logThing = (t: Thing) => {
  if (t.kind === "named") {
    // 여기서 t는 Named로 좁혀짐
    console.log(t.name);
  }
};
```

이 경우는 잘 작동하지만, 복잡한 타입 별칭이나 조건부 타입이 섞이면 타입스크립트가 좁혀진 타입을 인식하지 못할 수 있다.

#### Map의 `has()`와 `get()` 메서드

```typescript
const map = new Map<string, number>();
map.set("x", 1);

const key = "x";
if (map.has(key)) {
  const value = map.get(key); // value: number | undefined
  // 타입스크립트는 여전히 undefined를 포함함
}
```

**이유:**

1. 타입 시스템이 `has()`와 `get()` 메서드 사이의 논리적 연결을 보장할 수 없음
2. `has()` 체크 이후 Map이 변경될 가능성이 있음
3. Map의 제네릭 정의가 `get()`을 항상 `V | undefined`로 반환하도록 설계됨

**해결책:**

```typescript
// 방법 1: 커스텀 타입 가드
const getMapValue = <K, V>(map: Map<K, V>, key: K): V | null => {
  if (map.has(key)) {
    return map.get(key)!; // Non-null assertion (신중하게 사용)
  }
  return null;
};

// 방법 2: 변수에 할당
const value = map.get(key);
if (value !== undefined) {
  // value: number
}
```

### 아이템 23. 일관성 있는 별칭 사용하기

객체의 속성을 새로운 변수에 저장하면, **타입스크립트는 두 개를 독립적으로 추적한다**.

```typescript
interface Vector {
  x?: number;
  y?: number;
}

const getVector = (): Vector => ({ x: 1, y: 1 });

const vector = getVector();
let x = vector.x; // x: number | undefined

if (vector.x !== undefined) {
  // 조건문은 vector.x를 체크했지만
  x += 1; // 에러: x는 여전히 number | undefined
}
```

**왜 에러가 발생하는가?**

- 타입스크립트는 `vector.x` 조건을 확인했지만, **`x` 변수는 별개의 타입 체크를 진행**
- `x`의 타입은 좁혀지지 않음 (여전히 `number | undefined`)
- 중간에 `vector` 객체가 변경될 가능성을 배제할 수 없음

#### 해결책 1: 일관된 별칭 사용

```typescript
const vector = getVector();
let x = vector.x;

if (x !== undefined) {
  // x는 number로 좁혀짐
  x += 1; // 정상 작동
}
```

**단점:** 객체가 변경될 수 있을 때 문제 발생 가능

```typescript
if (x !== undefined && /* 다른 코드 실행 */ vector.x !== x) {
  // x와 vector.x가 동기화되지 않음
}
```

#### 해결책 2: 비구조화 할당

```typescript
const { x } = vector;

if (x !== undefined) {
  x += 1; // 타입 좁히기 정상 작동
}
```

**장점:**

- 변수와 프로퍼티를 명확히 분리
- 타입스크립트가 일관된 변수로 인식
- 코드의 의도가 명확함

**주의사항:**

```typescript
const vector: Vector | null = null;
const { x } = vector; // 에러: vector가 null일 수 있음

// 수정
if (vector !== null) {
  const { x } = vector; // 정상
}
```

### 아이템 24. 타입 추론에 문맥이 어떻게 사용되는지 이해하기

ts는 값이 존재하는 곳의 문맥까지도 살피지만, 가끔 문맥을 고려해 타입을 추론하면 이상한 결과가 나타남

```typescript
type Language = "JavaScript" | "TypeScript" | "Python"
function setLanguage(language: Lanaguage) {...}

setLanguate("JavaScript");

let language = "JavaScript";
setLanguage(language);
```

인라인 형태에서는 매개변수가 Language 타입이라는 것을 추론할 수 있음 -> 할당 가능하므로

근데 이걸 변수로 분리하면 할당 시점에 타입을 추론하므로,
여기서는 string 추론하고 Language 타입으로 할당 불가능하므로 오류가 발생했다.

> 왜 그런가?
> ts는 명시적인 타입 표기가 없더라도 지금 이 변수가 나중에 다른 문자열로 바뀔 수 있다고, 그러니까 재할당 가능성이 있다고 가정함
> 그래서 타입을 아주 구체적인

**해결 방법**

1. 타입 선언에서 할당가능한 값을 제한

```typescript
let language: Language = "JavaScript";
setLanguage(language);
```

2. const로 선언

```typescript
const language = "JavaScript";
setLanguage(language); // OK
```

**튜플에서는 얘기가 다름**

```typescript
const loc = [10, 20]; // number[]로 추론됨
```

const 썼는데도 number[]로 추론됨. [number, number] 튜플을 원했는데 안 됨

```typescript
const loc: [number, number] = [10, 20]; // 타입 명시
const loc = [10, 20] as const; // as const
```

> as const 쓰면 튜플로는 잡히는데 대신 readonly가 붙어버림
> 그래서 함수 쪽 매개변수도 readonly [number, number]로 받아줘야 함

**객체도 마찬가지**

객체 리터럴을 변수로 분리하면 내부 프로퍼티 값들이 넓은 타입(string 등)으로 추론돼서 문맥을 잃어버림. 콜백 함수도 마찬가지로 따로 빼내면 매개변수 타입 추론이 깨질 수 있음

> 결국 값을 어딘가에서 떼어내서 변수/상수로 분리하는 행위 자체가 문맥을 잃는 원인이 됨
> 이럴 땐 타입을 명시적으로 달아주자

### 아이템 25. 타입의 진화 이해하기

원래 타입은 변수 선언 시점에 정해지고 그 뒤로는 넓어지거나 좁아지지 않는다고 배웠음

근데 예외가 있음 -> **타입의 진화**

```typescript
function range(start: number, limit: number) {
  const nums = []; // 이 시점엔 any[]
  for (let i = start; i < limit; i++) {
    nums.push(i);
  }
  return nums;
  //     ^? number[]
}
```

nums는 선언될 때 any[]인데, push를 반복하면서 타입스크립트가 계속 지켜보다가 결국 number[]로 확정시켜버림

> 언제 진화가 일어나는가?
> 할당이 일어나는 바로 그 줄에서는 진화 X
> 그 다음 줄부터 진화된 타입이 반영됨

**몇 가지 특징**

- 여러 타입을 넣으면 유니온으로 진화함
- 조건문 분기 안에서도 동일하게 동작함
- any의 진화, let의 진화, 배열의 진화라고 부름
- forEach보다는 for-of나 map처럼 타입 흐름이 유지되는 구문을 쓰는 게 나음

> const로 선언하고 null, undefined를 넣으면 각자 그 타입으로 추론되는데
> let으로 선언하면 any로 새버릴 수 있음

**해결 방법**

암시적 any 상태를 오래 끌고 가지 말고, 명시적 타입 구문으로 처음부터 타입을 정해주는 게 안전함

> 타입을 안전하게 지키려면 결국 명시적 타입 구문!

### 아이템 26. 함수형 기법과 라이브러리로 타입 흐름 유지하기

같은 로직이라도 직접 루프 돌려서 짜는 것과 라이브러리(lodash 등) 함수형 기법으로 짜는 것은 타입 관점에서 결과가 다를 수 있음

**왜 서드파티 라이브러리가 유리한가?**

1. 타입 정의가 잘 되어 있어서 자동완성, 타입 검증이 자동으로 따라옴
2. 값이 파이프라인을 통과하는 동안 타입 흐름이 끊기지 않음
3. 직접 push하면서 값을 채우면 타입이 진화하는 과정에서 실수할 여지가 생기는데, 라이브러리 함수는 그 여지를 줄여줌

```typescript
// push는 타입 진화가 일어남
// concat은 항상 새 배열을 반환하므로 진화 자체가 발생하지 않음
```

> concat이 왜 다른가?
> push는 기존 배열을 변형(mutate)하니까 타입이 흐르면서 진화하는데
> concat은 새 배열을 만들어서 반환하니까 애초에 진화할 타입이 없음

**로대시(lodash) 체이닝**

```typescript
_(values).map(...).filter(...).uniq().value();
```

일반적으로 연산은 안쪽 함수부터 바깥쪽으로 계산되는 중첩 호출 순서인데, 체이닝은 이걸 뒤집어서 위→아래, 왼→오른쪽으로 읽히게 해줌 -> 가독성 좋아짐

값을 최종적으로 꺼낼 땐 `.value()` 호출 필요

> 이것도 결국 JS의 동작 방식을 최대한 그대로 모델링한다는 원칙과 맞닿아 있음

라이브러리 도입 자체가 오히려 코드를 복잡하게 만들거나 실익이 없다면 안 쓰는 게 나음. 근데 ts 환경에서는 "타입 추론이 얼마나 정확하게 유지되는가"라는 기준이 하나 더 있어서, 잘 만들어진 내장 함수/라이브러리 쪽을 쓰는 게 대체로 유리함
