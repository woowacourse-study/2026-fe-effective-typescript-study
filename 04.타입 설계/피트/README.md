무효한 상태: 서로 모순되는 값의 조합처럼, 실제로는 만들면 안 되는 상태

### 아이템 31: 문서에 타입 정보 쓰지 않기

주석에 디테일한 내용을 작성하지 말자. 코드와 주석은 동기화되지 않는다.

단위가 있는 숫자들은 예외이다. 예를 들어 `timeMs`

### 아이템 32: 타입 별칭에 `null` or `undefined` 포함하지 않기

타입 자체에 `null`을 포함한다면, 사용하는 부분에서는 항상 옵셔널 체이닝으로 검사해야 한다.

타입 체커에게는 문제가 되지 않지만, 사람이 보기에는 이해하기 힘든 경우가 생긴다.

그래서 `User | null` 형태가 더 일반적이다.

타입 별칭의 가장 바깥 부분에 드러나는 곳에 `null`을 포함시키지 말자.

> 타입 별칭은 무언가를 가리키는 용도로는 적절하지만, 무언가가 아닐 수도 있음을 표시하는 용도로는 적절하지 않다.

### 아이템 33: 타입 주변에 null 값 배치하기

의존 관계로 인해 `null`이 이어진다면, 이런 관계는 겉으로 드러나지 않기 때문에 개발자와 타입 체커 모두 혼란을 겪을 수 있다.

서로 한 묶음인 변수는 한 덩어리로 표현하자.

`min`, `max`를 계산해서 반환하는 메서드에는 결함이 존재한다. 첫 번째 예시 코드에서 반환 타입은 `(number | undefined)[]`로 추론되기 때문에, `min`이 존재해도 `max`가 존재하지 않을 수 있다.

이러한 타입을 `[number, number] | null`와 같이 모두 있거나 모두 없는 경우로 제한하면 사용하기 수월하다.

`null` 아님 단언문(`!`)이나 if 구문으로 체크할 수 있다.

클래스의 경우도 마찬가지이다. 속성 값의 불확실성이 클래스 전체에 나쁜 영향을 끼친다.

모든 값이 준비되었을 때 생성하는 것이 좋다.

## TS스터디 15일차: 아이템 34~35

### 아이템 34: 유니온의 인터페이스보다는 인터페이스의 유니온 사용하기

이 내용 또한 앞에서 자주 언급된 논리적 문제에 대한 이야기이다.

학생이라는 인터페이스에 옵셔널을 사용해서 개발자가 임의로 구분하게 구현한다면, 논리적인 오류가 발생할 수 있다.

그래서 학생과 선생님이라는 인터페이스를 따로 선언하고, `Person`이라는 타입에 유니온으로 조합해서 사용하면 이러한 논리적 오류를 줄일 수 있다.

어떤 특정 조합을 기대하는 경우 잘못된 조합으로 섞이는 경우를 방지하기 위해 각 조합을 인터페이스로 선언한 후, 그 인터페이스를 유니온으로 조합하는 타입을 선언하는 것이 바람직하다.

위 패턴의 가장 일반적인 예시는 `태그된 유니온`

하나의 타입에 이름을 명시해주는 맥락

어떤 데이터 타입을 태그된 유니온으로 표현할 수 있다면, 그렇게 하는 게 좋음

어떤 필드들이 관련되어 있다면, 객체로 모으는 것이 더 낫다.

```ts
interface Name {
  name: string;
}

interface PersonWithBirth extends Name {
  placeOfBirth: string;
  dateOfBirth: Date;
}
```

위 예시에서 두 인터페이스는 상속 관계라기보다는 `Name`의 속성을 포함한다는 개념

이름과 출생지는 있는데, 출생 날짜는 없는 이런 애매한 상황을 방지한다.

### 아이템 35: string 타입보다 더 구체적인 타입 사용하기

리마인드: 타입의 범위 = 그 타입에 할당 가능한 값의 집합

`string` 타입 남발에 관한 이야기이다.

`Date`나 몇 가지 경우만 존재하는 필드의 경우에도 `string`을 사용할 수 있지만, 남발이다.

그리고 남발 그 이상으로 오류를 발생시킬 수 있다.

`stringly typed`

제한할 수 있는 필드는 제한해보자.

명명된 타입을 사용하면 주석을 설명처럼 붙일 수 있다.

#### `pluck` 예시에서 이해가 잘 안 되는 부분

왜 `Album[keyof Album]`이 `string | Date` 타입이지?

마지막의 앨범 타입은 `live`, `studio` 두 리터럴의 유니온 아니었나? 결과값이 `string`이라서 그런가?

```ts
type Values = Album[keyof Album];

// 풀어서 보면
type Values =
  | Album['artist']
  | Album['title']
  | Album['releaseDate']
  | Album['recordingType'];

// 대입해보면
type Values = string | string | Date | ('studio' | 'live');
```

여기서 `"studio" | "live"`는 `string`의 부분집합이므로, `string`으로 퉁친다.

어쨌든 결과가 너무 넓다고 한다. 그래서 두 번째 제네릭 매개변수를 도입했다.

`string`은 `any`와 비슷한 문제를 가진다. 잘못하면 타입 관계를 감춰버린다!

### 아이템 36: 특수값에는 별도의 타입 사용하기

어떠한 행동의 실패와 성공이 구분되어 있다고 해도, 그 값들이 타입 정보와 함께 구분되기 어렵다면 버그를 일으켜도 타입 문제는 발생하지 않는다.

그래서 타입을 설계할 때는 특수값(`-1`, `0` 등)이 아니라, 태그된 유니온 패턴으로 특수한 상태를 표현하는 것이 더 좋은 방법이다.

### 아이템 37: 선택적 속성 지양하기

TS에서 옵셔널의 기본값은 항상 `undefined`

기존의 코드를 많이 변경하지 않기 위해서 옵셔널 필드를 추가하는 경우는 매우 흔하다.

그렇지만 옵셔널 필드를 추가하는 것보다는, 필수 필드로 추가해서 누락을 잡는 것이 더 안정성을 높이는 방법이다.

인터페이스에 옵셔널 필드를 추가할수록 `2^n`개의 조합 가능성이 생긴다.

API를 모델링하거나 수정하는 경우는 옵셔널 필드가 거의 필수적이다.

### 아이템 38: 같은 타입의 매개변수를 반복하지 않기

어떤 메서드든 동일한 타입의 매개변수가 연속해서 등장하면 타입 체커는 잘못된 입력을 구분할 수 없기 때문에 오류를 방지할 수 없다.

연관된 타입으로 분리하자!

또는 하나의 객체로 묶어서 전달하는 방식도 있다.

매개변수가 서너 개를 넘어간다면 그 순간부터는 리팩터링을 해야 한다.

ESLint에서 `max-params` 규칙으로 강제할 수 있음

> 인터페이스를 만들 때는 정확하게 사용하게 쉽게, 잘못 사용하기 어렵게 만들어라!

## TS스터디 17일차: 아이템 39~40

### 아이템 39: 타입 간 차이점을 모델링하기보다 같은 타입으로 통합하기

타입 차이점을 모델링하는 것보다 타입 간의 차이점을 없애는 것이 낫다.

이게 무슨 뜻일까? 아이템 37의 예시를 가져와보자.

```ts
interface InputAppConfig {
  darkMode: boolean;
  unitSystem?: UnitSystem;
}

interface AppConfig extends InputAppConfig {
  unitSystem: UnitSystem;
}
```

두 타입은 비슷하지만 다른 타입이다. 그래서 변환하는 메서드가 필수적이었다.

```ts
function normalizeConfig(input: InputAppConfig): AppConfig {
  return {
    ...input,
    unitSystem: input.unitSystem ?? 'imperial',
  };
}
```

기존 코드를 적게 수정하는 데 의미가 있지만, 계속 유지하면 복잡성이 생긴다.

같은 데이터에 대해 여러 타입이 생기게 되면, 개발자가 신경 써야 하는 부분들이 많아진다.

그래서 타입 차이를 없애라는 말은 DB의 매핑 기능을 사용하든, 클라이언트에서 데이터 타입을 통일하든 해서 하나의 데이터를 사용하도록 만들라는 말이다.

주의점: 타입 통일이 항상 가능한 것은 아니다. 체계적인 모델링이 필요한 경우가 있고, 맥락이 다른 타입을 억지로 묶는 것은 위험하다.

### 아이템 40: 부정확한 타입보다는 미완성 타입 사용하기

타입 선언을 세밀하게 할수록 꼭 좋은 것만은 아니다.

실제 데이터 규칙을 정확히 알아야 타입도 정확하게 만들 수 있다.

모든 것을 허용하는 타입은 타입 체커의 도움을 전혀 받지 못한다.

숫자, 문자열, 배열만 허용하는 타입은 boolean은 막지만, 배열 내의 값을 막지는 못한다.

함수 이름을 제한하는 타입은 첫 번째 인자가 연산자임을 잘 보장하지만, 인수의 개수와 타입은 여전히 막지 못한다.

또한 라이브러리와 타입 간의 결합도가 높아져서 수정 범위가 늘어난다.

함수별 인수까지 정확하게 표현하면 무효한 표현식을 더 많이 발견했기 때문에 훨씬 좋아진 것 같음

그러나 실제 언어에서는 연산자마다 규칙이 다를 수 있고, 무조건 인수가 2개가 아닐 수 있다.

즉, 타입을 정밀하게 만들었지만 실제 규칙을 잘못 모델링했음.

결론적으로, 타입이 복잡해질수록 타입 작성과 유지보수가 어려워지고, 타입 자체에도 버그가 생긴다. 또한 오류 메시지를 해석하는 일도 어려워질 수 있다.

#### 불쾌한 골짜기?

`any`처럼 너무 널널한 타입을 세밀하게 만들면 도움이 되지만, 너무 구체적이라고 해도 무조건 정밀도가 올라가지는 않는다.

규칙 자체가 복잡하다면 적당히 넓은 타입과 런타임 검증을 같이 사용하는 것이 좋다.

그래야 오류도 잘 잡고, 유지보수하기도 편할 것이다!
