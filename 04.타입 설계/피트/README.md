## TS스터디 13일차: 아이템 29~30

### 아이템 29: 유효한 상태만 타입으로 표현하기

타입 설계 시 어떤 값들을 포함하고 어떤 값들을 제외할지 신중하게 생각해야 한다.

#### 유효한 상태? 무효한 상태?

우리가 구현하면서 자주 실수하는 부분이라고 볼 수도 있을 것 같다.

예를 들어, 로딩 상태인데 데이터가 있다든지, 성공 데이터가 있는데 오류도 같이 있다거나 하는 실수를 방지해야 한다.

유효한 상태: 서비스 규칙상 실제로 일어날 수 있고 의미가 분명한 상태

무효한 상태: 서로 모순되는 값의 조합처럼, 실제로는 만들면 안 되는 상태

### 아이템 30: 엄격하게 생성하고 너그럽게 사용하기

매개변수 타입의 범위가 넓으면 편리하지만, 반환 타입의 범위가 넓으면 불편하다.

편리한 API일수록 엄격

#### `Iterable` 타입?

제너레이터 표현식에서 장점을 가진다.

순회 용도. 배열뿐만 아니라 집합 등도 받을 수 있음. 가장 넓은 타입

> 매개변수 타입의 범위를 유니온, `Iterable` 타입 등으로 넓혀서 사용하고, 반환 타입은 좁혀서 사용하자.

## TS스터디 14일차: 아이템 31~33

### 아이템 31: 문서에 타입 정보 쓰지 않기

주석에 디테일한 내용을 작성하지 말자. 코드와 주석은 동기화되지 않는다.

변수명에는 타입 정보를 넣지 말자. 변수와 타입을 따로 명시하자.

단위가 있는 숫자들은 예외이다. 예를 들어 `timeMs`

### 아이템 32: 타입 별칭에 `null` or `undefined` 포함하지 않기

타입 자체에 `null`을 포함한다면, 사용하는 부분에서는 항상 옵셔널 체이닝으로 검사해야 한다.

타입 체커에게는 문제가 되지 않지만, 사람이 보기에는 이해하기 힘든 경우가 생긴다.

그래서 `User | null` 형태가 더 일반적이다.

타입 별칭의 가장 바깥 부분에 드러나는 곳에 `null`을 포함시키지 말자.

> 타입 별칭은 무언가를 가리키는 용도로는 적절하지만, 무언가가 아닐 수도 있음을 표시하는 용도로는 적절하지 않다.

### 아이템 33: 타입 주변에 null 값 배치하기

의존 관계로 인해 `null`이 이어진다면, 이런 관계는 겉으로 드러나지 않기 때문에 개발자와 타입 체커 모두 혼란을 겪을 수 있다.

서로 한 묶음인 변수는 한 덩어리로 표현하자.

`min`, `max`를 계산해서 반환하는 메서드에는 결함이 존재한다. 첫 번째 예시 코드에서 반환 타입은 `(number | undefined)[]`로 추론되기 때문에, `min`이 존재해도 `max`가 존재하지 않을 수 있다.

이러한 타입을 `[number, number] | null`와 같이 모두 있거나 모두 없는 경우로 제한하면 사용하기 수월하다.

`null` 아님 단언문(`!`)이나 if 구문으로 체크할 수 있다.

클래스의 경우도 마찬가지이다. 속성 값의 불확실성이 클래스 전체에 나쁜 영향을 끼친다.

모든 값이 준비되었을 때 생성하는 것이 좋다.

## TS스터디 15일차: 아이템 34~35

### 아이템 34: 유니온의 인터페이스보다는 인터페이스의 유니온 사용하기

이 내용 또한 앞에서 자주 언급된 논리적 문제에 대한 이야기이다.

학생이라는 인터페이스에 옵셔널을 사용해서 개발자가 임의로 구분하게 구현한다면, 논리적인 오류가 발생할 수 있다.

그래서 학생과 선생님이라는 인터페이스를 따로 선언하고, `Person`이라는 타입에 유니온으로 조합해서 사용하면 이러한 논리적 오류를 줄일 수 있다.

어떤 특정 조합을 기대하는 경우 잘못된 조합으로 섞이는 경우를 방지하기 위해 각 조합을 인터페이스로 선언한 후, 그 인터페이스를 유니온으로 조합하는 타입을 선언하는 것이 바람직하다.

위 패턴의 가장 일반적인 예시는 `태그된 유니온`

하나의 타입에 이름을 명시해주는 맥락

어떤 데이터 타입을 태그된 유니온으로 표현할 수 있다면, 그렇게 하는 게 좋음

어떤 필드들이 관련되어 있다면, 객체로 모으는 것이 더 낫다.

```ts
interface Name {
  name: string;
}

interface PersonWithBirth extends Name {
  placeOfBirth: string;
  dateOfBirth: Date;
}
```

위 예시에서 두 인터페이스는 상속 관계라기보다는 `Name`의 속성을 포함한다는 개념

이름과 출생지는 있는데, 출생 날짜는 없는 이런 애매한 상황을 방지한다.

### 아이템 35: string 타입보다 더 구체적인 타입 사용하기

리마인드: 타입의 범위 = 그 타입에 할당 가능한 값의 집합

`string` 타입 남발에 관한 이야기이다.

`Date`나 몇 가지 경우만 존재하는 필드의 경우에도 `string`을 사용할 수 있지만, 남발이다.

그리고 남발 그 이상으로 오류를 발생시킬 수 있다.

`stringly typed`

제한할 수 있는 필드는 제한해보자.

명명된 타입을 사용하면 주석을 설명처럼 붙일 수 있다.

#### `pluck` 예시에서 이해가 잘 안 되는 부분

왜 `Album[keyof Album]`이 `string | Date` 타입이지?

마지막의 앨범 타입은 `live`, `studio` 두 리터럴의 유니온 아니었나? 결과값이 `string`이라서 그런가?

```ts
type Values = Album[keyof Album];

// 풀어서 보면
type Values =
  | Album['artist']
  | Album['title']
  | Album['releaseDate']
  | Album['recordingType'];

// 대입해보면
type Values = string | string | Date | ('studio' | 'live');
```

여기서 `"studio" | "live"`는 `string`의 부분집합이므로, `string`으로 퉁친다.

어쨌든 결과가 너무 넓다고 한다. 그래서 두 번째 제네릭 매개변수를 도입했다.

`string`은 `any`와 비슷한 문제를 가진다. 잘못하면 타입 관계를 감춰버린다!
