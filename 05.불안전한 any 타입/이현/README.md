## 아이템 43 any 타입은 가능한 한 좁은 스코프에서만 사용하기

`const pizza: any = getPizza();` 이 방식보다는
`eatSalad(pizza as any);` 이 방식이 조금 더 낫다

매개변수 안 스코프에서만 any가 되기 때문이다. 전자는 any로 선언한 것이 퍼지고 퍼져 큰 문제가 될 가능성이 높다.

객체 내부에 값 하나의 타입이 불분명하다면, 객체 전체를 any로 단언하지말고, 문제가 되는 타입만 any로 단언하자.

결국 any를 최대한 좁은 스코프에서만 쓰라는 제목이 핵심이다.

## 아이템 46 타입을 모르는 경우 any 대신 unknown 사용하기

```ts
function parseYAML(yaml: string): any {
  // ...
}

interface Book {
  name: string;
  author: string;
}
const book: Book = parseYAML(`
  name: Wuthering Heights
  author: Emily Brontë
`);
```

이렇게 타입 선언을 해주는 것보다 parseYAML 자체가 unknown을 반환하게 만드는 것이 더 안전하다.

unknown은 any 대신 쓸 수 있는 유용한 타입이다.
차이점이라면, unknown은 어떻게든 타입을 좁히지 않으면 사용할 수 없다는 것이다.

unknown의 친구중에는 `{}`타입이 있다. 이 타입은 unknown보다 좁다. null과 undefined를 제외한 모든 값이다.

결론은 any보다 unknown 쓰자

## 아이템 47 몽키 패치보다는 안전한 타입 사용하기

클래스에 임의의 속성 추가가능한 만큼 유연함

`런타임`에 객체 속성을 추가하는 것을 `몽키 패치`라고 부른다.

> JS 내장 기능의 프로토타입에도 속성을 추가할 수 있음.

근데 이렇게 몽키패치를 하게되면, 이게 전역변수가 되어서 멀리 떨어진 곳까지 에러가 번질 수 있음.

로그인된 사용자가 있음 (전역변수, window 객체에 user를 넣는 상황)
-> 여기선 당연히 타입 오류가 발생함

`(window as any ).user = user`로 해도 되지만, **interface의 타입 보강을 쓰면 됨!!**

보강은 좋아 보이지만 단점도 분명히 존재한다.

아래와 같은 상황이라면, user가 없을때 getUser()를 해도 런타임에 안정성을 보장받지 못한다.

```ts
interface Window {
  user: User;
}
```

따라서 이런식으로 undefined를 추가해서 더 안전하게 만들 수 있다.

```ts
interface Window {
  user: User  | undefined;;
}
```

보강의 또 다른 문제점이 존재한다.
바로 declare global 구문이 전역으로 적용되기 때문에 다른 파일이나 라이브러리로부터 타입을 감출 수 없다는 것이다.

이걸 해결하기 위해서는 window 타입을 확장해서 MyWindow같은 새로운 타입을 만드는 것이다.

그리고 나중에 타입 좁히기를 하면 된다.

## 아이템 48 무결성 함정 피하기

타입스크립트의 결함에 대해 알아보는 아이템이다.

타입 시스템이 정교할수록 무결성을 보장하기 힘들어진다.

타입 시스템의 표현력과 (무결성, 편의성)은 동시에 달성하기 어려운 트레이드 오프 관계이다.

무결성의 함정의 대표 예시 배열이 실제로는 원소 3개밖에 없는데. TS는 arr[3]을 런타임에 잡아내지 못함

배열과 마찬가지로 객체의 index 접근도 TS가 제대로 잡아내지 못함.
이걸 해결하려면 `noUncheckedIndexedAccess` 설정을 사용하면 됨.

이러면 편의성은 좀 떨어지지만, 대신에 무결성을 높여줌

클래스 계층의 이중변동성?

TS는 클래스의 메서드를 `이중변동`으로 모델링한다.
이 말은 "부모나 자식 메서드가 다른 한쪽으로 할당 가능하다면, 유효하다고 판다하는 것"이다.

-> 최대한 부모 메서드는 바꾸지 않는 것을 권장한다.
